# Amendment A4: pre-registered holdout confirmation `holdout-1`

**Status:** pre-registered plan, committed **before** any holdout run. It is a confirmation of the
exploratory gate results (A1–A3, [gate-confirm-1](../results/gate-confirm-1.md)) on fresh jobs. The
original `docs/PREREGISTRATION.md` is unchanged. **Not dispatched:** running it needs a separate
OWNER approval for spend and for the one workflow change listed below.

**2026-10-13, OWNER-APPROVED plan (no spend).**

## Why

The gate's A1 change was tuned on runs `38253007798` / `38285916667`, its live confirmation reused
that matrix's slots, and A3 was decided after seeing gate-confirm-1. Every gate number so far is
therefore exploratory. `holdout-1` tests the same claim on jobs nothing has been tuned on, with the
analysis and pass/fail thresholds fixed here first.

## What runs (fixed, generated by rule)

`tripwire/holdout.py` builds the committed list `runs/targets/holdout-1.json`
(`python -m tripwire.holdout --check runs/targets/holdout-1.json` verifies it offline):

* **Fresh fault draws.** The committed task set (`tasks/tasks_v1.json`) is re-planned with
  `tasks.fault_plan(..., seed=HOLDOUT_PLAN_SEED=20261013, 6 slots/task, 1/6 clean)`. The benchmark
  used seed 1, so fault assignments and per-run fault seeds (which decide the corrupted values) are
  new. Authoring refuses if any slot's (task, fault, fault_seed) equals a benchmark draw.
* **Never-seen job ids.** Every run id carries the `H1-` prefix; authoring refuses if any holdout job
  id is already in `runs/spend_ledger.jsonl`.
* **Selection, outcome-blind.** 3 slots per fault F1–F6 plus 6 clean slots (24 slots), in a seeded
  SHA-256 hash order, at most one slot per task per stratum.
* **Conditions.** Each slot runs under `baseline`, `prompt_fix` and `gate` (with A1's store
  cross-check and A3's turn-cap rule, as on `main`): **72 jobs**, grok-4.7, medium effort,
  client-side path.
* **Disclosure.** The tasks themselves are the committed v1 tasks (seen before); what is fresh is
  the fault draw, the corrupted values and the slot. A new task set would need a new dataset seed
  plumbed through the harness and is out of scope.

## Cost

* Estimate at the real observed ≈$0.075/run: 72 × $0.075 = **$5.40** (conservative; baseline runs

* Cumulative before: $39.32 of $50. After, at most **≈$45.32**.

## Primary metrics and pass/fail thresholds (fixed in advance)

Computed by `tripwire.report` (strict floor = excluded runs count as incorrect; published = excluded
runs dropped; 10,000-resample task-cluster bootstrap, seed 1) and applied by
`tripwire.holdout.evaluate`. All thresholds are inclusive point-estimate criteria:

| id | criterion | threshold |
| --- | --- | --- |
| P1 | gate all-faults **strict** minus prompt_fix all-faults strict | **≥ +10.0 points** |
| P2 | gate all-faults **published** | **≥ 90%** |
| P3 | gate clean false-flag rate (strict) | **≤ 1/6 (≤ 1 of 6 clean runs)** and ≤ prompt_fix's |
| P4 | gate $/correct (published) | **≤ 1.25 × prompt_fix's** |

**Verdict:** `PASS` if P1–P4 all hold; `FAIL` if any fails; `INCONCLUSIVE` if fewer than 72 records
were recorded or a source halted (no partial run is scored as PASS/FAIL). CIs are reported beside
every number but do not enter the verdict; with 18 faulted and 6 clean runs per condition they are
wide, and the holdout is a directional confirmation, not a precise estimate.

Secondary (reported, not part of the verdict): gate vs baseline, per-fault cells, turn-cap counts and
how many gate verdicts came from the A3 rule, total spend.

## Analysis (fixed)

`python scripts/holdout_report.py out/holdout-1-<run id> --out reports` writes
`reports/holdout_1.{md,json}` and `reports/holdout_1_verdict.json`. No exclusion rule, metric or
threshold may change after dispatch; any further analysis is labelled exploratory.

## Halts and errors

A `BUDGET_HALT`/`QUOTA_HALT` makes the run INCONCLUSIVE. Any top-up of unreached jobs needs a new
OWNER approval and is reported as such. `RUN_ERROR` runs stay in the strict denominator.

## Running it (needs approval; not done here)

The driver supports it (`python -m tripwire.live_eval --condition-set holdout-1 ...`, which verifies
the committed file and refuses `--targets`, `--pilot-jobs`, `--max-jobs` and budgets over $6).
**One workflow change is required**, separately approved: add `holdout-1` to the
`condition_set` choice options in `.github/workflows/live-eval.yml` (and its source
`docs/live-eval.workflow.yml`, plus the expected-text assertion in `tests/test_live.py`). Leave
`targets` blank. Then, dry run first:

```
gh workflow run live-eval.yml -f condition_set=holdout-1 -f budget_usd=5.80 \
  -f ledger_rows=1000 -f confirm=I-APPROVE-LIVE-SPEND -f dry_run=true
```

and the same with `dry_run=false` once the dry run is OK.
